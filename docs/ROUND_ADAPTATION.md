# 双屏适配说明（方屏 390×450 + 圆屏 390×390）

本工程是 **宽基指数行情 V2（appId 1126615）单工程双屏版**：同一套视图代码，
构建期按屏幕形状（`app.json` 的 `st`）各打包一份版面常量，方屏版面保持原样、
圆屏版面重新排布。运行期不做形状判断，只有一条代码路径。

- 方屏（`st="s"`）：390×450 设计画布，13 屏版面与改造前逐像素一致（见下文「回归证据」）
- 圆屏（`st="r"`）：390×390 设计画布，内容压进内接圆安全区
- 产物：`zeus build` 产出 12 个按「形状 × 分辨率」分组的 zpk
  （圆屏 360/416/454/466/480；方屏 320×380/390×450/432×514）

## 0. 目录与声明遵循官方规范

工程目录按官方 `docs/guides/architecture/folder-structure` 组织，屏幕适配按
`docs/guides/framework/device/screen-adaption` 的 v3 规范声明：

| 官方约定 | 本工程对应 |
| --- | --- |
| 一个构建目标，`platforms` 里写屏幕特征 | `app.json` → `targets.gt.platforms = [{"st":"r"},{"st":"s"}]` |
| `targets` 的键名 = `/assets` 子目录名前缀 | `gt` → `assets/gt.r/`、`assets/gt.s/` |
| 资源目录 `<target>.<配置限定符>` | `assets/gt.r/`（icon.png + fonts/）、`assets/gt.s/` 同构 |
| 版面文件 `[name].[配置限定符].layout.js`，与页面同目录 | `page/home/index.page.[pf].layout.js` 等 3 个页面各两份 |
| 页面「一目录一页面」，样式与行为分离 | `page/home/`、`page/universe/`、`page/detail/`，各自 `index.page.js` + 版面文件 |
| i18n 目录 `page/i18n/<语言>.po` | `page/i18n/` 下 34 个 `.po` |

`deviceSource` 在 configVersion v3 里**不是必需字段**（官方 app-json 标注为 "YES, v3 NO"）：
屏幕形状声明为 `st` 后，构建期自动为每档分辨率分包，因此不再逐个枚举设备型号。
原先手工维护的 18 个方屏 deviceSource 与 `gt.r`/`gt.s` 双 target 写法已按此规范合并。

> 早期用于圆屏移植的独立工程（`page/gt/` 目录结构、appId 24247）已合并进本工程，
> 其副本归档在工程外的 `_ETF2.0-归档/宽基指数ETF 圆屏-legacy/`。

## 1. 为什么圆屏需要重新排布，而不是等比缩放

视图层的坐标是**设计稿单位**（1 单位 = `app.json` `designWidth` = 390 下的 1px），
运行时由 `px()` 按屏宽缩放成设备像素。所以：

| 屏幕 | 设备像素 | 设计画布 | 说明 |
| --- | --- | --- | --- |
| 方屏 390×450 | 390×450 | 390×450 | 原版面就是按它设计的 |
| 方屏 432×514 | 432×514 | 390×464 | `px()` 按 432/390 放大 |
| 圆屏（任意） | 466×466 等 | **390×390** | 圆屏宽高相等 → 设计画布变成正方形 |

圆屏的设计画布高度比方屏**少 60 单位**（`px()` 只按屏宽缩放）。原版面内容带是
`y 64..422`，直接搬到 390 高的画布上会从屏底溢出 32 单位；再加上圆形显示区把四角切掉，
所以必须同时做两件事：**压缩纵向节奏** + **按弦宽收窄横向**。

## 2. 安全区：内切圆与弦宽

圆形显示区：圆心 (195,195)、半径 195（= 设计宽度的一半，因为圆屏直径就是屏宽）。

- **整块内容**（卡片带）取"整块同宽"的最大内接矩形：留 6 单位视觉余量后半径 189，
  `300 × 228` 的矩形四角半径为 188.4 < 189，正好贴住圆。**所有屏幕共用这一个矩形**
  （`x 45, y 81, w 300, h 228`），这样翻页时左右边距不跳动。
- **贴顶/贴边的元素**各自按所在行的弦宽收窄。半弦长 `√(R² - dy²)`：
  - 页头标题行（`y 34..62`，dy = -161）→ 可用宽度 **198**（`x 96..294`）；
    标题字号由 24 降到 20，"6 字标题 + 页码徽标"仍能一行放下
  - 页头副标题行（`y 63..79`，dy = -132）→ 可用宽度 **270**（`x 60..330`）
  - 列表滚动条（`x = 347`）落在屏幕中部，弦宽充足

圆屏 `CONTENT` 与方屏的对应关系（`utils/constants.js`）：

| 键 | 圆屏 | 方屏（390） |
| --- | --- | --- |
| x / width / margin | 45 / 300 / 45 | 16 / 358 / 16 |
| innerX / innerWidth | 58 / 274 | 29 / 329 |
| halfWidth / columnRightX | 144 / 201 | 173 / 201 |
| y / h（内容带） | 81 / 228 | 64 / 358 |
| scrollbarX | 347 | 376 |

## 3. 形状选择机制：`zosLoader [pf]`

Zepp OS 的官方做法（os3.0 模板同款）：

```js
import { ROUND, HEADER, METRICS, SCREENS as SCREEN_STYLE } from 'zosLoader:./shape.[pf].layout.js'
import { SCREEN_HEIGHT } from 'zosLoader:./index.page.[pf].layout.js'
```

zeus 在构建期把 `[pf]` 换成该屏幕特征的配置限定符（`st:"r"` → `r`），因此**圆屏包只含圆屏常量、
方屏包只含方屏常量**，视图层只有一条代码路径、不需要在运行时判断屏幕形状。

- `utils/shape.r.layout.js` / `utils/shape.s.layout.js`：形状样式表。
  含页头度量、CONTENT 缺口、以及 13 个屏幕的纵向节奏（`SCREENS.*`）。
  **两份表的键必须完全一致**（由 `tests/shape-layout.test.cjs` 锁定）。
- `page/<page>/index.page.[pf].layout.js`：页级布局文件，与页面同目录，只给设备像素层面的量
  （原生 swiper 页高、画布宽度）。
- 横向的 x/w 一律由 `CONTENT` 与 `columns(n, gap)` 推出，不写进样式表；
  `columns` 在 390 宽方屏下精确复现原值（2 列 → 16/201，3 列 → 16/139/262）。

  （方屏两者相同，圆屏画布正好等于屏高，避免画布被 `px()` 放大 20% 占内存）。

`verify:round` 对每一帧做三件事，任一不过就 exit 1：

1. **圆内**：所有元素（含被遮罩遮住的部分要扣掉，按绘制顺序判定）四角必须落在半径 195 的圆内。
2. **内容带**：文字横向必须落在 `x ∈ [45, 345]`。这条抓的是"位置仍在圆内、但已经出卡片带"的错位

3. **不叠字**：两块文字重叠面积超过较小者的 45% 就告警（按字号估算宽度，偶有保守误报）。

`preview/sheet-*.html` 是分页贴图（每页 10 帧），`preview/sheet-*.png` 是它的无头 Chrome 截图，
可直接打开做目视复查。**本次改造没有做人眼目视验收**（当前会话模型不支持图片输入），
视觉结论仅来自上述程序化检查。

### 回归证据（方屏未被带跑）

圆屏改造期间，把同一份离屏渲染器分别跑在**改造前的方屏工程**与**合并后的本工程**上，
逐帧字节比对 19 帧：

- 17 帧完全一致（两边的帧顺序、分节、画册排版也完全一致）
- 只有详情·行情图的两帧（分时/日K）存在**刻意修正**：
  底部信息条文字改为在信息条内居中（原来传的是 innerWidth，比信息条宽 19，文字偏右 9.5px）；
  MA 图例文字偏移改为与自身 14px 色线对齐（原来按默认 18px 偏移）。
- 圆屏帧：19 帧 0 失败 0 警告（圆内 + 内容带 + 不叠字三项全过）。
- 方屏越界签名：7 条，与改造前逐条一致（全部来自预警列表第 6 行滑到遮罩/屏底之下的那一段，
  属原有行为，数量与坐标完全相同）。

合并为单工程后，方屏这条比对不再需要"两份工程对跑"：`npm run verify:square` 直接拿记录的
基线签名逐条比对，多一条少一条或坐标变动都会 exit 1。

## 6. 详情页的内存约束与入口路由

Simulator（Amazfit Balance，480×480，JS 堆约 3.7 MB）上曾稳定复现"进详情页黑屏、
返回正常"。日志给出了确切原因：

```
js_trigger_gc *****rt->malloc_gc_threshold is now 3710120, malloc_size 2968096
InternalError: out of memory
js_rt_loadContiner2: failed to load .../page/gt/detail/index.page.js
switch_currentContainer: reset to pcid: 300000004
```

（上面的日志摘自圆屏移植期的独立工程，当时页面还在 `page/gt/` 目录下；合并为单工程后
路径变为 `page/detail/index.page.js`，其余现象与结论不变。）

即**详情页的页面容器申请失败**，框架回退到上一个容器，于是画面上什么都没有。
各页面编译后的设备端包体（`zeus build` 后解包 `.zab` 里的 `*.page.bin`，当前实测）：

| 页面 | 圆屏包 | 方屏包 |
| --- | --- | --- |
| 详情 | 105.5 KB | 106.4 KB |
| 首页 | 89.9 KB | 90.3 KB |
| 核心标的 | 61.3 KB | 62.1 KB |

（圆屏包略小于方屏包：形状样式表按 [pf] 分包，圆屏那份只含圆屏的纵向节奏与页头度量。
移植期对比过改造前的方屏工程，当时的量级是详情 109.9 KB / 首页 92.1 KB / 核心标的 62.9 KB。）

详情页是工程里最大的一个。对照实验（同一台模拟器、同一条路径）：

- 首页 → 核心标的 → **详情**：第三个容器申请失败（黑屏）。
- 首页 → 详情 → 核心标的、首页 → 首页 → 首页：都正常。
- 把详情页两个最重的视图（行情图、PE）临时去掉（包体降约 30 KB）后，同一条路径
  正常进入 —— 触发因素是详情页这个包本身。

顺带排除的两项：常驻场景从 3 降到 1（画布少三分之二）没有改善，说明画布内存不在
这块堆里；缓存预热从六个服务收回两个也没有改善。

因此入口做了两件事（`utils/navigation/route.js` 的 `safeReplace`、核心标的页的
`leaveToDetail`）：**用 replace 顶替当前页**（栈停在两层，和"首页 → 详情"等价），
并且**在导航前先把本页的场景/容器/控件交还出去**（Zepp 是先申请新容器再回收旧页面）。
代价：从详情返回落到首页，而不是回到核心标的的 8 只标的列表。
`npm run test:route` 锁住这条约定——它看不见、但改回 push 就会重新黑屏。

后续若要收回这个 UX 代价，方向是给详情页包体减负约 15 KB（主要来自每页都内联的
形状样式表：详情页只用到 13 屏里的 7 屏；另有若干已无引用的导出可删）。
